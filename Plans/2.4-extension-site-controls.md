# 2.4 — Extension site controls

Status: implementation plan, not shipped. The toolbar action host already
exists: action buttons, badges, popup presentation, pin/hide preferences, and
generated-fixture tests. Do not rebuild it.

## Scope and boundaries

- Add profile-local per-extension site-access policy beside existing host
  permission controls. Exact HTTP(S) host/origin matching; preserve independent
  extension enablement and toolbar visibility preferences.
- Verify WebKit's deny/grant semantics on the minimum supported SDK before
  selecting an enforcement design. Use current public APIs, with compiler and
  runtime gates for any newer member. An unenforceable switch must not ship.
- Explain the actual effect: page access denial is not disabling background
  extension execution. Already-injected page code may require a reload.
  Do not promise removal until a fixture proves it.
- Enforce policy at every relevant host/page exposure boundary, including
  activeTab, popups, tab adapters, and content-script access. A UI-only toggle
  is insufficient. Denial must win over later transient grant paths.
- No private-window controls or extension code. Never expose locked tab
  content, replace another window's presenter/bridge, or silently grant access.
- Persist explicit choices only; report failed writes. Resolve profile and
  site again before applying an async permission response.

## SDK enforcement spike — evidence report (2026-10-04)

Throwaway harness (`ExtensionInjectionSpike.swift`, `ExtensionActiveTabSpike.swift`,
since deleted): a generated MV3 extension with `host_permissions` and a
`document_end` content script setting `data-spike=1` plus a 100 ms heartbeat,
loaded into a `WKWebExtensionController(nonPersistent)` + `WKWebView`, pages via
`loadHTMLString(_:baseURL:)`. All runs on macOS 27 (Xcode 27, SDK with
`WKWebExtensionContext.setPermissionStatus`).

- S0 default: no explicit status, content script runs (injection allowed until denied).
- S1 granted pattern/URL before load: injected, status grantedExplicitly (+3).
- S2 denied pattern/URL before load: **not injected**, status deniedExplicitly (-3).
- S3 grant → load → deny without reload: the `data-spike` attribute stays and
  the heartbeat **keeps ticking** — already-injected code is not removed.
  After a fresh navigation ("reload"): **not injected**, status stays -3.
  → Denial needs a reload; the UI must say so honestly and never promise removal.
- S4 regrant + reload: injected again, status +3. Deny/regrant round-trips.
- S5/S5b `allURLs` granted + one host denied (either order): the denied host
  stays **not injected** at -3. → Host denial wins over broader grants.
- S6 sibling isolation: example denied, sibling granted → sibling injected,
  sibling status granted. No spillover.
- S7 granted-then-denied before load: not injected. Apply-on-load ordering works.
- S8a activeTab without deny: `userGesturePerformed` + `performAction` grants
  the tab's host. S8b activeTab with host denied: status stays -3 both globally
  and `in:` the tab after the gesture. → Denial wins over activeTab.

Enforcement design selected: `setPermissionStatus(.deniedExplicitly, for:)`
per host pattern (both `https://host/*` and `http://host/*`) on load and on
every change; `.grantedExplicitly` for Allow; `.unknown` to clear back to Ask.
Prompt delegates consult the stored map first (deny → answer empty without
prompting; allow → grant without prompting) and re-resolve after the user's
answer, so a denial stored mid-prompt wins over the tap.

## Test-first acceptance

Generated extension and local fixture page: allowed access, denied DOM/script
access, deny after injection with honest reload state, reload retains deny,
regrant restores access, activeTab cannot bypass deny, sibling host isolation,
two-profile separation, private/locked exclusions, stale permission prompt,
and failed persistence. Keep all existing action-host tests green.

## Delivery

SDK enforcement spike with an evidence report; pure policy/repository; host
wiring; Settings/site-shield controls. If enforcement cannot be demonstrated,
leave the feature open and report the limitation instead of shipping a label.
